Modelos de orquestração de agentes

Um agente resolve conversa aberta. Um processo tem etapas. O framework traz cinco padrões prontos para coordenar vários agentes; a escolha quase sempre se resume a uma pergunta: quem decide o próximo passo, você ou o modelo? Clique em um padrão para ver quando usar e o código.

Qual padrão usar?

Use um agente quando…

  • a tarefa é aberta ou conversacional;
  • precisa de planejamento e uso autônomo de tools;
  • uma chamada ao modelo (com tools) resolve.

Use um workflow quando…

  • o processo tem etapas bem definidas;
  • você precisa controlar a ordem de execução;
  • vários agentes ou funções precisam se coordenar.

Se dá para resolver com uma função, escreva a função. Agente é para o que não cabe numa função.

--  Domínio: cadastro de clientes, endereços e pedidos (cenário de
--  atendimento / atualização cadastral usado pelos agentes).
--  Compatível com PostgreSQL 14+.

CREATE SCHEMA IF NOT EXISTS workshop;
SET search_path TO workshop, public;

-- ---------------------------------------------------------------------
-- Tipos
-- ---------------------------------------------------------------------
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'status_pedido') THEN
        CREATE TYPE status_pedido AS ENUM (
            'pendente', 'pago', 'enviado', 'entregue', 'cancelado'
        );
    END IF;
END$$;

-- ---------------------------------------------------------------------
-- Clientes
-- ---------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS clientes (
    id              SERIAL PRIMARY KEY,
    cpf             CHAR(11)      NOT NULL UNIQUE,
    nome            VARCHAR(120)  NOT NULL,
    email           VARCHAR(160)  NOT NULL UNIQUE,
    telefone        VARCHAR(20),
    segmento        VARCHAR(40)   NOT NULL DEFAULT 'varejo',
    criado_em       TIMESTAMPTZ   NOT NULL DEFAULT now(),
    atualizado_em   TIMESTAMPTZ   NOT NULL DEFAULT now()
);

-- ---------------------------------------------------------------------
-- Endereços (1 cliente pode ter vários; um é o principal)
-- ---------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS enderecos (
    id              SERIAL PRIMARY KEY,
    cliente_id      INT          NOT NULL REFERENCES clientes(id) ON DELETE CASCADE,
    cep             CHAR(8)      NOT NULL,
    logradouro      VARCHAR(160) NOT NULL,
    numero          VARCHAR(10)  NOT NULL,
    complemento     VARCHAR(60),
    bairro          VARCHAR(80),
    cidade          VARCHAR(80)  NOT NULL,
    uf              CHAR(2)      NOT NULL,
    principal       BOOLEAN      NOT NULL DEFAULT TRUE,
    origem          VARCHAR(20)  NOT NULL DEFAULT 'manual',   -- manual | viacep | agente
    criado_em       TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- Garante um único endereço principal por cliente
CREATE UNIQUE INDEX IF NOT EXISTS ux_enderecos_principal
    ON enderecos (cliente_id) WHERE principal;

-- ---------------------------------------------------------------------
-- Pedidos
-- ---------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS pedidos (
    id              SERIAL PRIMARY KEY,
    cliente_id      INT            NOT NULL REFERENCES clientes(id) ON DELETE CASCADE,
    codigo          VARCHAR(20)    NOT NULL UNIQUE,
    descricao       VARCHAR(200)   NOT NULL,
    valor           NUMERIC(12,2)  NOT NULL CHECK (valor >= 0),
    status          status_pedido  NOT NULL DEFAULT 'pendente',
    criado_em       TIMESTAMPTZ    NOT NULL DEFAULT now(),
    previsao_entrega DATE
);

CREATE INDEX IF NOT EXISTS ix_pedidos_cliente_status ON pedidos (cliente_id, status);

-- ---------------------------------------------------------------------
-- Log de ações dos agentes (trilha de auditoria da demo)
-- ---------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS log_agentes (
    id              BIGSERIAL PRIMARY KEY,
    agente          VARCHAR(60)  NOT NULL,
    acao            VARCHAR(60)  NOT NULL,
    cliente_id      INT          REFERENCES clientes(id) ON DELETE SET NULL,
    detalhes        JSONB,
    criado_em       TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- ---------------------------------------------------------------------
-- Trigger: mantém atualizado_em
-- ---------------------------------------------------------------------
CREATE OR REPLACE FUNCTION trg_set_atualizado_em() RETURNS TRIGGER AS $$
BEGIN
    NEW.atualizado_em := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS clientes_atualizado_em ON clientes;
CREATE TRIGGER clientes_atualizado_em
    BEFORE UPDATE ON clientes
    FOR EACH ROW EXECUTE FUNCTION trg_set_atualizado_em();

-- ---------------------------------------------------------------------
-- View de apoio: visão consolidada do cliente (usada pelas tools)
-- ---------------------------------------------------------------------
CREATE OR REPLACE VIEW vw_cliente_resumo AS
SELECT
    c.id,
    c.cpf,
    c.nome,
    c.email,
    c.segmento,
    e.cep,
    e.logradouro,
    e.numero,
    e.bairro,
    e.cidade,
    e.uf,
    COUNT(p.id) FILTER (WHERE p.status IN ('pendente','pago','enviado')) AS pedidos_abertos,
    COALESCE(SUM(p.valor) FILTER (WHERE p.status IN ('pendente','pago','enviado')), 0) AS valor_em_aberto
FROM clientes c
LEFT JOIN enderecos e ON e.cliente_id = c.id AND e.principal
LEFT JOIN pedidos  p ON p.cliente_id = c.id
GROUP BY c.id, e.cep, e.logradouro, e.numero, e.bairro, e.cidade, e.uf;

"""
Cria o esquema e carrega os dados de demonstração em um PostgreSQL
já existente (alternativa ao docker-compose, para quem tem um
Postgres local, Azure Database for PostgreSQL etc.).

Uso:
    python scripts/setup_db.py            # usa DATABASE_URL do .env
    python scripts/setup_db.py --reset    # dropa o schema antes

DATABASE_URL no formato:
    postgresql://usuario:senha@host:5432/workshop
"""

from __future__ import annotations

import argparse
import os
import sys
from pathlib import Path

import psycopg
from dotenv import load_dotenv

ROOT = Path(__file__).resolve().parents[1]
SQL_DIR = ROOT / "sql"


def main() -> int:
    load_dotenv(ROOT / ".env")

    parser = argparse.ArgumentParser(description="Cria e popula o banco do workshop.")
    parser.add_argument("--reset", action="store_true", help="dropa o schema 'workshop' antes de recriar")
    args = parser.parse_args()

    url = os.getenv("DATABASE_URL")
    if not url:
        print("DATABASE_URL não definida. Veja .env.example.", file=sys.stderr)
        return 1

    scripts = sorted(SQL_DIR.glob("*.sql"))
    if not scripts:
        print(f"Nenhum .sql encontrado em {SQL_DIR}", file=sys.stderr)
        return 1

    with psycopg.connect(url, autocommit=True) as conn:
        if args.reset:
            print("• Removendo schema 'workshop'…")
            conn.execute("DROP SCHEMA IF EXISTS workshop CASCADE")

        for script in scripts:
            print(f"• Executando {script.name}…")
            conn.execute(script.read_text(encoding="utf-8"))

        with conn.cursor() as cur:
            cur.execute("SET search_path TO workshop")
            cur.execute(
                """
                SELECT 'clientes', COUNT(*) FROM clientes
                UNION ALL SELECT 'enderecos', COUNT(*) FROM enderecos
                UNION ALL SELECT 'pedidos', COUNT(*) FROM pedidos
                """
            )
            for tabela, total in cur.fetchall():
                print(f"  {tabela:<10} {total:>4} linhas")

    print("✔ Banco pronto.")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

Etapa 6

O agente que você não enxerga não vai para produção

A telemetria é OpenTelemetry com as convenções GenAI. O mesmo código do cenário 1 roda instrumentado; só o destino muda por variável de ambiente. No Foundry, o trace aparece em Build ▸ Agents ▸ Traces e as métricas em Monitor.

from agent_framework.observability import configure_otel_providers, get_tracer

client = get_client()
if OBS_TARGET == "foundry":

Pontos para a fala

  • Um span pai por requisição de negócio; abaixo dele, workflow → agente → modelo → tool, com tokens e latência por nó.
  • enable_sensitive_data=True grava prompts e respostas nos spans. Ótimo em demo, decisão de governança em produção.
  • A tabela log_agentes é a trilha de auditoria no banco; o trace é a trilha técnica. Em ambiente regulado, as duas se complementam.
  • Agente rodando fora do Azure? Registre como custom agent no Foundry e envie com o mesmo gen_ai.agent.id; aparece no mesmo monitor.
